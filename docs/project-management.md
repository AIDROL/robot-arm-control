# 项目代码与协作方案

## 仓库边界

项目组 GitHub Organization 已建立为 [AIDROL](https://github.com/AIDROL)，建议其下按交付物建立仓库。Organization 用于管理成员、权限和多个仓库；本地文件夹用于放一个仓库的工作副本。当前目录已经是 Git 仓库，无需再套一层文件夹或重复 `git init`。

| 仓库建议名 | 主要内容 | 维护者 |
| --- | --- | --- |
| `robot-arm-control`（本仓库） | xArm7 仿真、运动规划、视觉定位、抓取任务、真实机械臂适配 | 机械臂算法控制负责人 |
| `mechanical-design` | 台架、夹具、末端执行器的 CAD 源文件、工程图、机械 BOM | 机械负责人 |
| `electronics-control` | 电气原理图、接线图、嵌入式程序、电子 BOM、硬件接口 | 电控负责人 |

先只建立有负责人和实际内容的仓库。跨领域接口文档可以先放在相关仓库中，并用链接相互引用；当系统集成工作成为独立交付物时，再建立 `system-integration` 仓库。不要把论文作者的 GitHub 仓库直接复制进本仓库；记录出处、版本和许可证，并通过依赖或明确的引用使用。

## 本仓库应保存什么

- `simulation/`：MuJoCo 模型配置与可复现的仿真任务；当前只有单关节基线。
- 后续按需要增加 `control/`、`perception/`、`hardware/`、`docs/`，分别放控制算法、视觉定位、真实机器人适配和接口约定。不要预先创建空目录。
- 统一记录坐标系、单位、关节顺序、TCP 定义、相机外参、夹爪开闭含义；真实硬件接入前需与机械和电控负责人共同确认。
- `.venv/`、缓存、日志、生成的视频与大批量原始相机数据不入 Git。确需版本化的大型 CAD 或实验数据应讨论 Git LFS 或外部数据存储，并在文档中记录版本和获取方法。

## 协作流程

1. 每项可验收的工作建一个 Issue，写明目标、负责人、输入、完成标准；跨领域任务在相关仓库的 Issue 中互相链接。
2. `main` 保持可运行。每项工作从 `main` 开短分支，提交小而清晰的 commit；通过 Pull Request 合并。团队开始多人协作后，为 `main` 设置至少一人 review 和必要的运行检查。
3. PR 描述应包括改动、运行或验证方式、仿真与真实硬件之间尚未验证的假设。涉及坐标系、线缆、夹具、工作空间或安全边界时，请对应负责人 review。
4. 用版本标签标记能重现的演示或阶段成果，例如 `v0.1-sim-baseline`；实验记录写明 Git commit、依赖版本、模型/标定版本。
5. 用一个 GitHub Project 跟踪跨仓库任务。列可从“待办 / 进行中 / 待评审 / 完成”开始，避免在三个仓库各维护一份互不一致的总计划。

## 第一阶段任务

1. 已有：xArm7 模型加载、Home 姿态、单关节受控运动、无界面运行检查。
2. 下一步：末端位姿读取、目标位姿与逆运动学、关节限制及可达性检查。
3. 再下一步：桌面、目标物和末端夹具的简化模型；已知物体位姿的抓取和放置。
4. 然后：虚拟相机与标记定位，建立相机到机器人基座的坐标变换。
5. 硬件确定后：替换实际机械臂、夹具和相机参数；对接 SDK，做低速、受限的实机验证。

## 需要团队确定的事项

- Organization 的管理：确认 AIDROL 由实验室/项目组持续管理，而非仅依赖某个成员；至少两位可信任的 Owner。
- 仓库可见性：采购、未发表成果及实验室资料未确认可公开前，建议先设 Private。
- 三个领域的维护者及跨领域接口审批人。
- CAD、大文件和实验数据的存储位置、备份方式与共享范围。
